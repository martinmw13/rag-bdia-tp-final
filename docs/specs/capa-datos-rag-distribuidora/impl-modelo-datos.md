# Especificación de implementación: modelo de datos y arquitectura

## Propósito

Definir qué estructuras y contratos debe materializar la capa de datos. Esta especificación fija requisitos técnicos; el plan posterior decidirá el orden de construcción y la organización exacta de los scripts.

## Áreas y archivos a investigar

- `CONTEXT.md`, como vocabulario canónico del dominio.
- `docs/diagramas/`, como destino de los modelos Mermaid conceptual, lógico, físico y de arquitectura.
- `db/estructura/`, como autoridad del esquema físico.
- `db/indices_vistas/`, como autoridad de índices, vistas y estructuras de acceso.
- `practica/postgres/`, como referencia de estilo para PostgreSQL, pgvector y `EXPLAIN ANALYZE`, sin copiar su dimensión vectorial ni su dominio.

## Plataforma y límites arquitectónicos

- La prueba funcional debe usar una única instancia de PostgreSQL con las extensiones `vector` y `btree_gist`.
- PostgreSQL debe concentrar datos operativos, metadatos documentales, embeddings, permisos, interacción y auditoría.
- Los archivos Markdown originales deben permanecer fuera de la base y vincularse mediante rutas relativas portables, tamaño, MIME type y SHA-256.
- No forman parte de la implementación un Data Warehouse, Data Lake, Lakehouse, almacenamiento de objetos, réplica, particionamiento físico, API, interfaz o LLM.
- El flujo de datos debe mostrar: generación sintética, carga, documento/versionado, fragmentación, embeddings, recuperación autorizada, evidencia y auditoría.

## Convenciones físicas

- Nombres `snake_case` en español.
- Claves internas `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Códigos de negocio únicos en Producto, Cliente, Proveedor, Pedido y Documento.
- Asociaciones puras con claves primarias compuestas.
- Instantes con `TIMESTAMPTZ`; posiciones y órdenes con `INTEGER`; actividad con `BOOLEAN`.
- Importes y porcentajes con `NUMERIC` de precisión y escala explícitas; importes no negativos y descuentos entre 0 y 100.
- Texto obligatorio protegido contra cadenas vacías cuando corresponda.
- Historial protegido con `ON DELETE RESTRICT`; maestros y catálogos se desactivan con `activo`.
- Intervalos de vigencia semiabiertos: `[vigente_desde, vigente_hasta)`.

## Catálogos requeridos

| Estructura | Contrato mínimo |
| --- | --- |
| `categoria_producto` | Código, nombre y actividad. |
| `segmento_cliente` | Código, nombre y actividad. |
| `perfil_autorizado` | Código, nombre y actividad. |
| `clase_documental` | Código, nombre, descripción y actividad. |
| `nivel_sensibilidad` | Código, nombre, indicador de auditoría y actividad. |
| `modelo_embedding` | Nombre, versión, dimensión, métrica y actividad; unicidad por nombre y versión. |

Los estados pequeños y cerrados deben expresarse mediante restricciones controladas y no mediante catálogos adicionales. Para la prueba, todos los modelos de embedding tienen dimensión 32 y como máximo uno participa en búsquedas vigentes.

## Núcleo operativo

| Estructura | Relaciones y restricciones principales |
| --- | --- |
| `producto` | Pertenece obligatoriamente a una categoría; código único; actividad. |
| `cliente` | Pertenece obligatoriamente a un segmento; código único; actividad. |
| `proveedor` | Código único; actividad. |
| `producto_proveedor` | Asociación N:M opcional, sin pares duplicados. |
| `condicion_comercial` | Cliente, producto, precio, descuento y vigencia; sin solapamiento por par cliente-producto. |
| `pedido` | Código único, cliente, fecha y estado. |
| `linea_pedido` | Número dentro del pedido, producto, cantidad y snapshots de precio/descuento; producto no repetido por pedido. |
| `entrega` | Código único, pedido, fechas y estado; admite entregas parciales. |
| `incidencia_operativa` | Código único, entrega, fecha, tipo, descripción y estado. |

Un pedido persistido como unidad de negocio válida debe tener al menos una línea. La carga y las operaciones que crean pedidos deben validar esa condición de manera atómica; no se requiere forzarla mediante una restricción local imposible de expresar.

## Núcleo documental y vectorial

| Estructura | Contrato mínimo |
| --- | --- |
| `documento` | Código, título, clase, sensibilidad, procedencia y actividad. |
| `version_documental` | Documento, número, estado, vigencia, hitos de publicación/revocación y contrato del archivo original. |
| `fragmento` | Versión, posición, contenido y página opcional; posición única por versión. |
| `embedding` | Fragmento, modelo, `VECTOR(32)` e instante de generación; un vector por fragmento-modelo. |
| `documento_producto` | Asociación opcional a nivel documento, sin duplicados. |
| `documento_proveedor` | Asociación opcional a nivel documento, sin duplicados. |

Los estados documentales permitidos son `borrador`, `publicada`, `sustituida` y `revocada`. No deben existir períodos publicados vigentes superpuestos para un documento. Borradores, sustituidas y revocadas permanecen en el historial, pero quedan fuera de la recuperación vigente.

Sólo los fragmentos se vectorizan. Un fragmento puede conservar embeddings de modelos históricos distintos, pero nunca más de uno para el mismo modelo. La evidencia debe poder fijar el embedding exacto que participó en la respuesta.

## Interacción y evidencia

| Estructura | Contrato mínimo |
| --- | --- |
| `actor` | Código, nombre, único perfil autorizado y actividad; sin credenciales. |
| `consulta` | Actor, perfil efectivo, pregunta e instante. El perfil debe coincidir con el perfil vigente del actor; no se admiten delegaciones en el TP. |
| `respuesta` | Cero o una por consulta; tipo de resultado, contenido e instante. |
| `resultado_estructurado` | Tipo de consulta predefinida, parámetros, snapshot, instante y hash; no contiene SQL arbitrario. |
| `evidencia_documental` | Respuesta, embedding exacto, ranking y score; sin repetición dentro de la respuesta. |
| `evidencia_estructurada` | Respuesta y resultado estructurado; sin pares repetidos. |
| `evento_auditoria` | Actor, perfil efectivo, instante, acción, resultado, recurso, correlaciones y detalles variables. |

Los tipos de resultado mínimos son `exito`, `sin_resultados`, `sin_fuente_autorizada` y `acceso_denegado`. Una respuesta `exito` debe finalizar su transacción con al menos una evidencia; los tipos negativos no deben tener evidencia.

## Uso permitido de JSONB

JSONB se limita a:

- `version_documental.metadatos`;
- `resultado_estructurado.parametros`;
- `resultado_estructurado.contenido`;
- `evento_auditoria.detalles`.

Cualquier atributo usado regularmente para identificar, relacionar, autorizar, validar o filtrar debe permanecer tipado y normalizado. No se requieren índices GIN porque las consultas representativas no filtran dentro de estos documentos JSONB.

## Integridad e invariantes transaccionales

- Reglas locales: nulabilidad, claves, unicidad, rangos y claves foráneas.
- Reglas temporales: exclusión de solapamientos en condiciones comerciales y versiones documentales.
- Publicar una versión debe cambiarla a vigente y sustituir la anterior en una única transacción.
- Una versión no puede publicarse con fecha futura respecto del instante efectivo de la operación.
- La carga de una versión debe fallar si falta el archivo, difieren tamaño o checksum, o la relación uno a uno no puede demostrarse.
- Los objetos históricos de interacción, evidencia y auditoría no deben borrarse en cascada.

## Índices y vistas requeridos

- Índices B-tree únicamente para claves foráneas, joins, filtros y correlaciones usados por las consultas acordadas, evitando duplicados con índices de PK, unicidad o exclusión.
- Índice HNSW sobre `embedding.vector` con `vector_cosine_ops` y parámetros predeterminados.
- Vista normal de fragmentos recuperables con semántica `security_invoker`, que reúna fragmento, versión, documento, modelo y permisos sin eludir RLS.
- No se requieren vistas materializadas ni precálculos persistentes.

## Casos límite obligatorios

- Pedido cancelado sin entrega y pedido válido con entregas parciales.
- Documento sin vínculo a producto o proveedor.
- Dos embeddings del mismo fragmento pertenecientes a modelos diferentes.
- Versión revocada sin reemplazo y sustitución de una versión vigente.
- Condición vencida, vigente y futura para combinaciones controladas.
- Código duplicado, FK inexistente, descuento inválido y períodos superpuestos rechazados.
- Archivo ausente o con checksum incorrecto rechazado antes de completar la carga.

## Criterios de aceptación

- El modelo Mermaid y el esquema físico representan las mismas entidades y cardinalidades relevantes.
- Las restricciones declarativas rechazan todas las operaciones inválidas acordadas.
- Las invariantes transaccionales no dejan estados intermedios observables.
- Los embeddings son trazables hasta el fragmento, la versión, el documento y el modelo.
- La arquitectura puede ejecutarse localmente sin componentes distribuidos ni servicios de IA.
