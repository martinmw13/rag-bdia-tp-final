\section{Propuesta de arquitectura de datos}

La arquitectura usa una instancia de PostgreSQL para datos operativos,
metadatos documentales, embeddings, permisos, interacciones y auditoría. Las
extensiones \texttt{pgvector} y \texttt{btree\_gist} agregan búsqueda vectorial
y restricciones temporales sin sumar otro motor.

Un solo motor combina relaciones, vigencia, autorización y similitud en la
misma consulta. Separar la base relacional de la vectorial obligaría a duplicar
y sincronizar metadatos, sin una ventaja comprobable para esta escala.

La Figura~\ref{fig:arquitectura} resume el recorrido. El generador produce el
SQL de datos, los documentos Markdown y un manifiesto con conteos, checksums y
oráculos. El cargador aplica el esquema, los datos, los índices, las vistas y la
seguridad. Una aplicación futura podrá usar el rol de ejecución. El frontend,
la API y la integración con un LLM quedan fuera de la implementación mínima.

Los documentos quedan fuera de PostgreSQL. La base guarda su ruta relativa,
procedencia, tamaño, tipo MIME y checksum. Así pueden trasladarse más adelante a
almacenamiento de objetos sin cambiar el control de integridad.

No se incorpora un Data Warehouse, Data Lake ni Lakehouse porque las consultas
son operativas y los datos son pocos. Si se necesitaran análisis históricos a
otra escala, los hechos y eventos podrían copiarse a una capa analítica.
